# Публичный доступ без VPS: Cloudflare quick tunnel

Задача F1-10: человек открывает сервер на своём ноуте, остальные заходят как на
сайт — из любой сети, без проброса портов, домена и аккаунта Cloudflare.

## Как это работает

Поднимается **один** туннель, и через него идут и страница, и WebSocket:

| Что | Локальный порт | Наружу |
| --- | --- | --- |
| игровой сервер (Colyseus) + собранный клиент | 2567 | `https://<random>.trycloudflare.com` |

Адрес выдаёт Cloudflare при старте (`trycloudflare.com`, без логина).
Его нужно **вшить в сборку клиента** до `npm run build`, потому что адрес
известен только после старта туннеля:

```bash
echo "VITE_SERVER_URL=wss://<tunnel-host>" > packages/client/.env.production
npm run build -w @oasis/client
```

Клиент отдаёт сам сервер (`packages/server/src/index.ts`): если
`packages/client/dist/index.html` существует, express.static включается сам.
Раньше статика поднималась отдельным `serve` на 8080 с **вторым** туннелем —
и это была ошибка: страница и WebSocket оказывались на разных доменах.

Почему один домен обязателен: бесплатные туннели показывают страницу
предупреждения и запоминают согласие **кукой на своём домене**. При двух
адресах пользователь мог пройти предупреждение только на первом, а его
WebSocket шёл на второй — и игра не подключалась, молча, без единой ошибки
в консоли.

## Грабли на этой машине

Здесь **две** разные беды, выясненные по очереди (25.10 и 26.10):

1. `cloudflared` не может зарезолвить `api.trycloudflare.com` — системный
   systemd-resolved отдаёт `no such host`, а `/etc/hosts` править нельзя (нет
   прав). При этом через `1.1.1.1` имя резолвится нормально.
2. Даже когда имя резолвится, системный DNS отдаёт для `api.trycloudflare.com`
   `185.61.104.70/71`, а до этих адресов соединение **сбрасывается/таймаут**
   (режется на уровне сети). Рабочие anycast-адреса Cloudflare отвечают:
   `104.16.100.100`, `172.64.32.1`, `104.20.1.1` → `200`; `162.159.140.220` и
   `172.66.0.218` → `403` (чужой роут на API); `185.61.104.x` → таймаут.

Обход обеих: запускать `cloudflared` в mount-namespace, подменив и
`/etc/resolv.conf`, и `/etc/hosts` (юзернеймспейсы включены, root не нужен):

```bash
printf 'nameserver 1.1.1.1\nnameserver 8.8.8.8\n' > /tmp/resolv-cf.conf
{ cat /etc/hosts; echo '104.16.100.100 api.trycloudflare.com'; } > /tmp/hosts-cf
unshare -rm bash -c \
  'mount --bind /tmp/resolv-cf.conf /etc/resolv.conf && \
   mount --bind /tmp/hosts-cf /etc/hosts && \
   exec cloudflared tunnel --no-autoupdate --edge-ip-version 4 --url http://localhost:PORT'
```

Если API снова перестанет отвечать — IP подбирается вручную:

```bash
for ip in 104.16.100.100 172.64.32.1 104.20.1.1; do
  curl -s -m 8 --resolve api.trycloudflare.com:443:$ip \
    -o /dev/null -w "$ip %{http_code}\n" -X POST https://api.trycloudflare.com/tunnel
done
```

Рабочий IP задаётся переменной `CF_API_IP`, всё это завёрнуто в
`scripts/tunnel.sh`.

## Резерв: pinggy, если Cloudflare недоступен

`api.trycloudflare.com` в какой-то момент может быть закрыт совсем (или
сам домен `*.trycloudflare.com` режется у игроков — это уже случалось),
тогда `deploy.sh` сам (за 15 секунд) переключается на SSH-туннель pinggy
(`scripts/tunnel-pinggy.sh`, аккаунт не нужен):

- плюс: поднимается из любого места, где открыт SSH на 443;
- плюс: **играть можно** — после одного клика «Enter site» на странице
  предупреждения туннель ставит кукой согласие, и дальше проходят и
  страница, и WebSocket (проверено: `deploy-check` сам жмёт эту кнопку);
- минус: кука живёт 10 минут, поэтому при перезагрузке страницы кнопку
  просят нажать снова (уже открытая игра при этом не рвётся);
- минус: адрес туннеля живёт 60 минут, потом нужен повторный `deploy.sh`.

Выбор принудительно: `TUNNEL=cloudflare scripts/deploy.sh` или
`TUNNEL=pinggy scripts/deploy.sh`.

Отдельно проверялось и отвергнуто: localtunnel (`loca.lt`) просит ввести
свой публичный IP, serveo и tunnelmole не пропускают `Upgrade: websocket`
(страница открывается, игра — нет), localhost.run требует ключ.

## Проверка, что деплой действительно играется

`curl 200` ничего не доказывает: туннель может отдавать статику, а WebSocket
— молча не проходить (ровно так ломалось). Полная проверка:

```bash
node scripts/deploy-check.mjs        # берёт адреса из .deploy-state
```

Она открывает публичную ссылку в headless-chromium, при необходимости сама
нажимает кнопку входа на странице предупреждения туннеля, ждёт «в сети»,
поднимает второго игрока и проверяет ростер и видимые тела. Для
`trycloudflare.com` хосты маппятся через `--host-resolver-rules` (локальный
DNS отдаёт адрес, до которого соединение не доходит); остальные туннели
резолвятся сами — их карта ломает сертификат. Код выхода 0 — деплой играется.

## Запуск

Всё в одну команду:

```bash
scripts/deploy.sh
```

Скрипт делает ровно эту последовательность и печатает ссылку:

1. останавливает старые процессы на 2567/8080/5173, если висят;
2. поднимает сервер и его туннель — ждёт появления `https://` в логе
   (15 с на cloudflare, иначе pinggy);
3. пишет `packages/client/.env.production` с этим адресом и собирает клиент
   (проверяет, что адрес реально попал в бандл);
4. пишет состояние в `.deploy-state` и делает `curl` на страницу и на
   WS-хэндшейк → печатает ссылку и два HTTP-кода.

Статику поднимать не нужно: сервер отдаёт `packages/client/dist` сам.

Порядок важен: адрес туннеля выдаётся только при старте туннеля, а он
вшивается в бандл на этапе сборки — поэтому сервер и туннель идут раньше
клиента. Сборка после старта сервера безопасна: express.static читает файлы
с диска на каждый запрос, перезапуск не нужен.

Вручную (тот же порядок, если нужно точечно):

```bash
node_modules/.bin/tsx packages/server/src/index.ts &   # :2567
scripts/tunnel-pinggy.sh 2567 /tmp/pg.log              # или scripts/tunnel.sh
grep -oE 'https://[a-z0-9-]+\.(free\.pinggy\.net|trycloudflare\.com)' /tmp/pg.log

echo "VITE_SERVER_URL=wss://<хост из лога>" > packages/client/.env.production
npm run build -w @oasis/client
```

Сервер обязан слушать `0.0.0.0` (по умолчанию так, `HOST=0.0.0.0`).
`.deploy-state` — runtime-состояние (адреса меняются при каждом запуске),
в git не входит.

## Ограничения

- URL меняются при каждом перезапуске туннеля — клиент надо пересобирать.
- Туннель живёт, пока жив процесс и ноут; это не постоянный хостинг.
- Quick tunnel без SLA. Для фазы 2 — VPS + named tunnel или свой сервер.
- Проверка снаружи: `curl https://<client>/` → 200, WS-хэндшейк на сервер →
  `101`; окончательно — `node scripts/deploy-check.mjs` (см. выше).
