# Архитектура OASIS Core

> Проект: федеративная платформа виртуальных миров. Веб-клиент, протокол-first.
> Все цифры без источника — **оценка**; обоснования и цифры — в `07-sources.md`.

---

## 1. Главный тезис: «безграничность» — это не размер

**[оценка]** «Безграничный мир» решается набором из четырёх техник, и ни одна из них
не требует много серверов:

| Приём | Что даёт | Сложность |
|---|---|---|
| **Шардинг по секторам** | Мир режется на независимые секторы; каждый сектор — свой процесс/под | Низкая |
| **Interest management (AOI)** | Клиенту не отправляется весь мир, а только область интереса | Средняя |
| **Процедурная генерация** | Контент генерируется, а не хранится: бесконечная планета = функция от координат | Низкая |
| **Мир как данные** | Мир = версионированный JSON/глоссы, а не бинарный ассет-бандл | Низкая |

**Дорого стоят:** контент (наполнение руками), комьюнити, экономика и модерация.
Поэтому «сделать Оазис на 100 человек» — реальная задача, а «сделать Оазис с 10 млн
и 50 мирами» — это в первую очередь задача контента и людей, а не кода.

## 3. Сервисы

### 3.1 Core (несколько, дешёвые, долгоживущие)

| Сервис | Ответственность | Состояние |
|---|---|---|
| **Identity** | Регистрация, вход, сессии, 2FA, восстановление | Postgres |
| **World Registry** | Каталог миров, версии, зоны, флаги правил, модерация публикации | Postgres |
| **Economy (ledger)** | Единственный источник истины по валюте: append-only проводки, эмиссия, эскроу | Postgres (append-only таблица) |
| **Social** | Друзья, чат, presence, репутация | Postgres + Redis |
| **Asset Service** | Загрузка/выдача ассетов, версионирование, CDN | S3 + CDN |
| **Moderation** | Жалобы, автомодерация, санкции, аудит-лог | Postgres |
| **Telemetry** | Метрики, логи, ошибки | Prometheus/ClickHouse-лайт |

**[оценка]** Правило: **всё, что можно сделать одной транзакцией в Postgres, — одна
транзакция.** Не вводить микросервисы ради микросервисов: у нас 2 человека.

### 3.2 Sector (масштабируемая, «горячая» часть)

Сектор — это игровой шард одного мира: под-процесс со своей симуляцией и своей
подпиской на сетевые события.

- **Один сектор = один pod** (в k8s) или один процесс (на VPS). Горизонтальное
  масштабирование = добавить сектор.
- Сектор **не знает** о других секторах. Межсекторные переходы — через Gateway
  (пересадка игрока = «переключение сессии»).
- **Флаги правил** живут в конфиге сектора: `pvp`, `magic`, `tech`, `teleport`,
  `comms` — прямо из канона (27 секторов с разными правилами).

**[реальность]** Для оркестрации игровых серверов есть готовый инструмент:
**Agones** — проект от Google, переехал в **CNCF** (23.03.2026), поддерживает
label-based allocation, health checks, allocation API. Для нашей задачи это ровно то,
что нужно, когда секторов станет больше десятка.

### 3.3 Что НЕ микросервис

**[оценка]** Ни в коем случае не делать отдельными сервисами: чат (идёт через WebSocket
внутри сектора), инвентарь (это часть ledger), античит клиента (клиент не доверенный —
значит, вся валидация на сервере), редактор миров (это веб-приложение + Asset Service).

## 4. Протокол (это главное архитектурное решение)

**[оценка] Протокол-first: клиент — тонкий, сервер — источник истины, формат данных
версионируется.**

### 4.1 Требования

1. **Один протокол — много клиентов.** Сегодня веб, завтра нативный/VR — тот же протокол.
2. **Версионирование.** `protocol_version` в хендшейке; несовместимые изменения — v2.
3. **Сервер-авторитет.** Клиент никогда не решает, что произошло. Клиент — это
   «предсказание + интерполяция», а не источник состояния.
4. **Формат — компактный и стабильный.** В коде сегодня: свой бинарный
   кодек (`BIN_CHANNEL`, 19 байт на сущность) поверх WebSocket плюс JSON на
   control-plane. protobuf и msgpack не подключены — свой кодек уже покрывает
   трафик, сторонний формат понадобится, когда появится внешний клиент.
   (WebTransport — когда дойдёт до массовой поддержки, но WS — база сейчас.)
5. **Мир как данные.** Сектор и клиент читают **одно и то же** описание мира.

### 4.2 Формат мира

```
content/default/world.json — версионированный, верхний уровень ровно семь ключей
├─ id: "default"
├─ version: 1
├─ seed: 20261021
├─ generator: "oasis-v1"
├─ sectors:  [ { id, name, flags: {pvp, magic, tech, teleport, comms}, spawn: {x,y,z} } ]
├─ zones:    [ { id, sectorId, name, kind, bounds: {x,z,w,d},
│               groundColor,
│               props: [ { id, type, x, y, z, sx, sy, sz, rot, color } ] } ]
└─ portals:  [ { id, fromZone, toZone, x, z, radius } ]
```

Сейчас в мире 1 сектор, 3 зоны и 4 портала, 324 пропа. Отдельных ключей
`meta`, `assets`, `entities`, `ext` **нет**: активы лежат прямо в `zones[].props`,
спавн — в `sectors[].spawn`, портальные связи вынесены в `portals`.
`zone` (полная, с `props`) приходит отдельным сообщением по запросу
`zone_request`, а в `welcome` поле `world.zones` — без `props`: заголовок
мира остаётся единицами килобайт.

**[оценка] Ключевой приём: мир = чистые данные + seed + версия генератора.**
Тогда:
- процедурный мир воспроизводится из seed (нулевое хранение контента);
- старый мир открывается старым клиентом (совместимость);
- «другой редактор» или «другой хостер» может прочитать тот же JSON — **это и есть
  фундамент federation**.

### 4.3 Трафик: снапшоты + дельты

**[оценка]** Стандартная схема, проверенная MMO-школами:

- сервер шлёт **снапшот** состояния сектора при входе игрока (или при переподключении);
- дальше — **дельты** по подписке (interest management);
- клиент **интерполирует** между последними известными состояниями;
- при расхождении (prediction fail) — клиент шлёт свою позицию обратно, сервер
  корректирует (server-side reconciliation).

Частота снапшота: **10 Гц** (`SNAPSHOT_RATE`), тик сервера — 20 Гц, дельты
уходят тем же батчем 10 раз в секунду. Размер дельты: единицы-сотни байт на
объект (в бинарном канале — ровно 19 байт на сущность).

### 4.4 Interest management (AOI)

**[оценка]** Мир режется на **сетку** (grid cells). У каждого игрока есть подписка
на клетки в радиусе R (например, 2–3 клетки). Сервер рассылает объекты только
подписчикам.

Иерархия (от дешёвого к дорогому):

| Уровень | Радиус | Что видно |
|---|---|---|
| L0 «я» | 0 | Свой аватар, свой инвентарь |
| L1 ближний | ~10–15 м | Персонажи вокруг, чат, взаимодействия |
| L2 средний | ~50 м | Здания, машины, пропсы |
| L3 дальний | ~300 м | Силуэты, крупные объекты (low LOD) |
| L4 «мир» | ∞ | Только метаданные: карта, список миров, чат-каналы |

**[оценка]** Это и есть техническая «безграничность»: клиент получает столько данных,
сколько нужно его камере, а не столько, сколько есть в мире.

## 5. Хранилище

| Данные | Где | Почему |
|---|---|---|
| Миры (JSON-версии) | Postgres (`world_versions`) | Нужны транзакции и поиск по каталогу |
| Валюта | Postgres, **append-only** (`ledger_entries`) | Единственный источник истины; баланс = материализованная сумма |
| Ассеты | S3/MinIO → CDN | Раздача — на CDN, сервер не проксирует байты |
| Presence, сессии, pub/sub | Redis | Быстро, эфемерно, дешёво |
| Снапшоты секторов | S3 (периодически) | Восстановление после падения |
| Логи/метрики | ClickHouse-lite / Loki-лайт | Аналитика без нагрузки на прод |

**[канон] Ledger как append-only — прямо из экономической модели канона:** валюта
должна быть «одной из самых стабильных в реальном мире», а такая стабильность
невозможна без проверяемой истории проводок.

## 6. Стек (v1, минимальный)

| Слой | Выбор | Почему |
|---|---|---|
| Язык сервера | **TypeScript / Node.js** | Один язык с клиентом, быстрый старт, дешёвый деплой |
| Транспорт | **WebSocket (Colyseus)** + свой бинарный кодек | Просто, дёшево, достаточно; protobuf не нужен — 19 байт на сущность |
| Игровой фреймворк | **Colyseus** (или Nakama) | Сервер-авторитет, комнаты = секторы, tick-loop, snapshot/delta из коробки |
| Клиент | **Three.js + WebGPU** (или Babylon.js) | Зрелые, огромная экосистема, WebGPU-путь есть |
| БД | **PostgreSQL** | JSONB для мира, транзакции для ledger, партиционирование по миру |
| Кэш/сессии | **Redis** | Presence, pub/sub между секторами, rate limit |
| Ассеты | **MinIO** (локально) → S3 + CDN | Совместимость с S3 = лёгкий миграция |
| Оркестрация | docker-compose → **Agones** (когда понадобится) | Уже в CNCF, решает allocation секторов |
| Песочница UGC | **WASM** (WASI) в отдельном процессе/контейнере | Изоляция кода пользователей |
| Наблюдаемость | Prometheus + Grafana (или проще: Loki + Grafana) | Минимум на старте |

**[реальность 27.10]** Живёт в `main` только верх таблицы: Node, Colyseus со
своим бинарным кодеком, Three.js + `WebGPURenderer` (с откатом на WebGL2).
Ledger по умолчанию в памяти — `STORAGE=memory`; `PostgresLedger` уже написан
и включается `STORAGE=postgres` + `DATABASE_URL`. Redis, MinIO, docker-compose
и Prometheus **не подключены**: они появятся вместе с шардингом (фаза 2) и
тем, что в них реально хранить и мерить.

**[оценка]** Wasmtime / wasm3 / Wasmer — для запуска пользовательских скриптов (логика
предметов, механики зон) в песочнице. WASM-песочница — это то, что отличает
«платформу» от «игры»: правила мира пишутся пользователями, но исполняются в
контейнере без доступа к ФС и сети.

## 7. Federation — отличие от Roblox

**[оценка]** Это главный продуктовый и архитектурный ответ на «Roblox — не то».

| | Roblox | OASIS (наш замысел) |
|---|---|---|
| Что продукт | Приложение-платформа | **Протокол** + ядро |
| Кто держит миры | Только Roblox | Ядро держит **ядро миров**, миры может хостить **третье лицо** по нашему протоколу |
| Личность и имущество | Привязаны к Roblox-аккаунту | **Переносимы**: идентичность и активы живут в ядре, клиент/хост — сменные |
| Ассеты | Roblox-создатели (Robux) | UGC на открытых форматах + свои правила |
| Выход | Robux → DevEx → USD (только для разработчиков, с KYC) | **Closed loop в v1**, open loop — в v2, с лицензиями |
| Культура | Экосистема внутри одной платформы | Федерация миров с разными законами |

**[реальность]** Тренды в мире подтверждают, что запрос на это есть:
W3C **Metaverse Interoperability Community Group**, **Metaverse Standards Forum**
(W3C присоединился в 2022), **Open Metaverse Browser Initiative** («Sneeze»,
SIGGRAPH 2026) — все работают над переносимостью идентичности и данных между мирами.

**[оценка]** Реалистичный горизонт federation:
- v1 — один мир, один хостер (мы);
- v2 — «мир как файл»: любой может опубликовать свой JSON-мир, но хостит только он;
- v3 — сторонний хостер, наш протокол, общий ledger, переносимая личность.

## 8. Секьюрность и античит (базовый уровень)

**[оценка]** Клиент недоверенный, поэтому:

1. **Сервер решает всё** — движение, попадания, экономика. Клиент шлёт только intent.
2. **Скорость ограничена** по дистанции: `max_speed * dt + tolerance`.
3. **Лимит действий** в секунду (rate limit) на уровне Gateway и на уровне игровых действий.
4. **Двусторонняя валидация** экономических операций (server-side escrow).
5. **Аудит** изменений мира и ledger — append-only, с actor id.
6. **[реальность]** Формат `Universal Commerce Protocol`/Open metaverse пока сырой;
   **[оценка]** базовый уровень защиты — это вовсе не античит, а сервер-авторитет.

## 9. Что сознательно НЕ закладываем

- Свой **полноценный физдвижок** (rigid body, джоинты, трение) — не
  закладываем: для v1 коллизии капсулы решает свой небольшой резолвер
  `resolvePlayerMove` в `packages/protocol/src/collision.ts` (AABB/OBB/круги,
  шаг вверх, опора, присед) — один и тот же на сервере и в предсказании
  клиента. Rapier/cannon-es — первый кандидат, когда появятся динамические
  объекты; физика при этом всегда авторитетная, на сервере.
- Свой сетевой код UDP/QUIC — слишком рано; WebSocket + биндинг перейдём на WebTransport,
  когда будет нужен.
- Своя CDN — берём дешёвую (Cloudflare и т.п.) и файлы отдаём из S3.
- Kubernetes как обязательное требование — compose на одном VPS, k8s/Agones — когда
  секторов станет >10 и появдутся деньги.
