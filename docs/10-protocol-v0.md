# Протокол OASIS v0.2.0

> Это **не** RFC и не финальная спецификация. Это контракт между нашим
> сервером и нашим клиентом на сегодня, записанный так, чтобы его можно было
> реализовать на другом языке, не читая исходники.

Версия: `0.2.0` · Тик: 20 Гц · Снапшоты: 10 Гц · Ввод: 30 Гц · AOI: 24 м

---

## 1. Модель

Три плоскости, разделённые намеренно:

| Плоскость | Транспорт | Частота | Что внутри |
|---|---|---|---|
| **Состояние** | бинарный канал `bin` | 10 Гц | позиции, курс, флаги игроков в AOI |
| **Управление** | JSON-сообщения | по событию | welcome, roster, chat, zone, teleport, balance, error |
| **Статика** | JSON `zone` по запросу | редко | геометрия зоны: пропсы, границы, цвет земли |

Почему так:

- **Бинарный канал** — потому что это единственное, что летит постоянно.
  19 байт на сущность против ~120 байт JSON. При 50 игроках в AOI и 10 Гц
  разница — 9.5 КБ/с против 60 КБ/с на игрока.
- **Имена отдельно** (`roster`) — меняются раз в сессию, незачем платить за них 10 раз в секунду.
- **Статика отдельно** (`zone`) — 333 объекта на три зоны. Гонять их в снапшотах
  бессмысленно: они не двигаются. Клиент получает дескриптор один раз и строит сцену.

Сервер — единственный источник истины. Клиент предсказывает **только** своего
игрока и только между подтверждениями.

## 2. Транспорт

WebSocket (Colyseus 0.18, `@colyseus/ws-transport`). Matchmaking — HTTP
`POST /matchmake/joinOrCreate/sector`, тело — JSON с параметрами входа.

Комната одна: `sector`. В v0 один мир = один сектор = одна комната.
Шардинг по секторам — следующая итерация (см. `02-architecture.md`).

### Handshake (обязателен)

```
клиент                                  сервер
  │  POST /matchmake/joinOrCreate        │
  │  { protocolVersion, accountId,       │
  │    accountCreatedAt, name }          │
  │ ───────────────────────────────────► │  проверка версии, лимита, схемы
  │ ◄─────────────────────────────────── │  seat reservation
  │  WS connect                          │
  │ ◄─────────────────────────────────── │  JOIN_ROOM (sessionId, roomId)
  │  room.send('hello', {protocolVersion})│
  │ ───────────────────────────────────► │  создать сущность, ledger,
  │                                      │  welcome + roster + snapshot
  │ ◄─────────────────────────────────── │
```

**Почему нужен отдельный `hello`.** Colyseus подтверждает вход (`JOIN_ROOM`)
*после* выполнения `onJoin`. Всё, что сервер отправит внутри `onJoin`, придёт
раньше, чем клиентский `await joinOrCreate()` разрешится и повесит обработчики —
сообщения потеряются. Явный `hello` убирает гонку: клиент сначала регистрирует
обработчики, потом просит мир.

Таймаут: если `hello` не пришёл за 10 с — сервер закрывает соединение (`4002`).
Если версия не совпала — `4001` и сообщение `error` с кодом `PROTOCOL_MISMATCH`.

Версия сравнивается **строго**. Разный layout бинарных пакетов = мусор вместо
координат, поэтому «совместимость на глаз» здесь не работает.

## 3. Бинарный канал

Канал называется `bin`. Первый байт пакета — тип.

### 3.1. Заголовок

| Смещение | Тип | Поле |
|---|---|---|
| 0 | u8 | тип пакета: `1` snapshot, `2` delta |
| 1 | u32 | `tick` (номер серверного тика) |
| 5 | u16 | количество сущностей `n` |

Далее `n` записей по 19 байт.

### 3.2. Сущность (19 байт)

| Смещение | Тип | Поле | Примечание |
|---|---|---|---|
| 0 | u32 | `id` | ID сущности в секторе, стабилен на сессию |
| 4 | u8 | `kind` | `0` prop, `1` player |
| 5 | u16 | `flags` | битовая маска (см. ниже) |
| 7 | i16 | `x` | метры × 64 |
| 9 | i16 | `y` | метры × 64 |
| 11 | i16 | `z` | метры × 64 |
| 13 | u16 | `yaw` | 0..65535 → 0..2π |
| 15 | u32 | `color` | 0xRRGGBB |

Всё little-endian.

Квантование позиции — 1/64 м (1.5625 см). Это компромисс: i16 хватает на
±512 м, чего с запасом хватает зоне (максимум в дефолтном мире — 100×100 м).
Позиции за пределами диапазона **зажимаются**, а не переполняются.

`yaw` кодируется в 16 бит: 65536 шагов на 360° = 0.0055° на шаг. Для куколки
без анимации — избыточно, но байт всё равно кратен четырём, и округление не стоит ничего.

Флаги:

| Бит | Имя | Смысл |
|---|---|---|
| 0 | `Moving` | модуль скорости > 0.1 м/с |
| 1 | `Sprinting` | бег |
| 2 | `Speaking` | печатает в чат (задел на индикатор) |

### 3.3. Delta (от `snapshot`)

После массива сущностей:

| Тип | Поле |
|---|---|
| u16 | количество удалённых `m` |
| u32 × m | id, которые вышли из области интереса |

Дельта считается **на сессию**: сервер хранит `Map<entityId, lastSentState>` и
шлёт только изменившиеся сущности. Если ничего не изменилось — пакет не
отправляется вовсе (на 10 Гц это заметная экономия в статичной сцене).

`snapshot` приходит один раз при активации сессии; дальше — только `delta`.
Полный снапшот — способ ресинхронизироваться после разрыва.

### 3.4. Ввод (C→S, 12 байт)

| Смещение | Тип | Поле |
|---|---|---|
| 0 | u8 | тип `3` |
| 1 | u32 | `seq` (монотонный) |
| 5 | i16 | `dirX` × 1000 |
| 7 | i16 | `dirZ` × 1000 |
| 9 | u16 | `yaw` (доля полного оборота) |
| 11 | u8 | флаги: `1` — спринт |

`dirX/dirZ` — уже нормализованный вектор в **мировых** координатах, `yaw` —
курс камеры. Направление взгляда и направление движения разные: можно идти
спиной вперёд. Сервер нормализует вектор и ограничивает скорость; значения
`dir` за пределами ±1 не ошибка, а просто нормализация.

Клиент реально шлёт бинарный ввод (`Connection.sendInput`). JSON-путь
`C2S.Input` остался как отладочный: он проходит ту же симуляцию, но
валидируется схемой и при провале рвёт соединение (так устроен Colyseus).
Боевой путь — бинарь; валидация там своя, в `decodeInput` + нормализации.

## 4. JSON-сообщения (control plane)

### C→S

| Имя | Payload | Валидация |
|---|---|---|
| `hello` | `{ protocolVersion }` | zod, строка 1..32 |
| `input` | `{ seq, dirX, dirZ, yaw, sprint }` | zod, `dirX/dirZ` ∈ [−1,1] |
| `chat` | `{ text }` | zod, 1..240 символов, rate limit |
| `zone_request` | `{ zoneId }` | zod, строка 1..64 |
| `ping` | `{ t }` | zod, конечное число |
| `rename` | `{ name }` | zod, строка 1..24, обрезка и чистка на сервере |

### S→C

| Имя | Payload | Когда |
|---|---|---|
| `welcome` | `WelcomeMsg` | ответ на `hello` |
| `roster` | `{ players: [{id, name, color}] }` | вход/выход игрока |
| `chat` | `{ from, name, text, ts }` | сообщение в чат (эхо отправителю тоже) |
| `zone` | `{ zone: ZoneDef }` | ответ на `zone_request` |
| `teleport` | `{ zoneId, position }` | вход в радиус портала |
| `balance` | `{ balance, reason }` | изменение баланса |
| `pong` | `{ t }` | ответ на `ping` |
| `renamed` | `{ name }` | ответ на `rename`; `name` — выданный сервером ник (может отличаться) |
| `error` | `{ code, message }` | отказ/ошибка |

`WelcomeMsg`:

```ts
{
  protocolVersion: '0.2.0',
  playerId: 7,              // id сущности, не sessionId
  sessionId: 'abc123',
  world: {                  // заголовок без геометрии
    id: 'default', version: 1, seed: 20261021,
    generator: 'oasis-procgen/1',
    sectors: [...],
    zones: [{ id, name, kind, bounds, groundColor }],  // без props
    portals: [{ id, fromZone, toZone, x, z, radius }]
  },
  sectorId: 's_plaza',
  tickRate: 20, snapshotRate: 10, aoiRadius: 24,
  spawn: { x, y, z },
  balance: 100
}
```

`world.zones` — **без** `props`. Геометрия приходит по `zone_request`.
Это ключевое решение: заголовок мира — единицы килобайт, полный мир — сотни.

Коды ошибок:

| Код | Когда |
|---|---|
| `BAD_HELLO` | join-параметры не прошли схему |
| `PROTOCOL_MISMATCH` | версия не равна серверной |
| `SECTOR_FULL` | игроков ≥ лимита сектора |
| `NO_SECTOR` | в мире нет ни одного сектора |
| `NO_ZONE` | запрошена несуществующая зона |
| `CHAT_TOO_FAST` | превышен rate limit чата (не чаще 1 сообщения в секунду) |
| `INTERNAL` | ошибка на стороне сервера при активации сессии |

Провал zod-схемы (например, `hello` с `name` из 100 символов) — это не
`error`-сообщение: Colyseus закрывает соединение с кодом `WITH_ERROR`.
Поэтому схемы ввода и чата намеренно мягкие: сервер нормализует и обрезает
данные сам, а не наказывает клиента разрывом. `chat` длиннее 240 символов
обрезается, а не отклоняется.

## 5. Область интереса (AOI)

- Радиус `AOI_RADIUS = 24 м` по плоскости XZ. Y не учитывается: зоны плоские.
- **Своя сущность всегда в кадре**, даже если вы стоите на краю мира.
- Попал в радиус → приходит в следующей дельте. Вышел → приходит `removed`.
- Портал, чат и ростор **не** зависят от AOI: это control plane, а не мир.

При 64 игроках и радиусе 24 м в AOI реально находятся единицы-десятки.
Считаем по кругу, а не по сетке: сетка окупается от сотен сущностей, до этого
`O(n)` дешевле, чем поддержка индекса.

Что **не** входит в AOI и почему:

- **Пропсы.** Они статичны и приходят один раз дескриптором зоны. Если в будущем
  появятся динамические объекты (двери, транспорт), они станут сущностями с
  `kind: Prop` и попадут в поток автоматически.
- **Имена.** Отдельный `roster`, потому что строка на игрока 10 раз в секунду —
  это ровно тот трафик, который мы экономим бинарным форматом.

## 6. Тик и движение

```
сервер: setFixedTimestep(dt => simulate(dt), 20)
        setInterval(publish, 100ms)

клиент: accumulator += frameDt
        while (accumulator >= 50ms) { predict(); accumulator -= 50ms }
```

Скорости: `PLAYER_SPEED = 5 м/с`, `PLAYER_SPRINT_SPEED = 8 м/с`, ускорение
`PLAYER_ACCEL = 28 м/с²`, торможение `PLAYER_DECEL = 42 м/с²`. Разгон и
торможение живут в одной чистой функции `stepVelocity` в `@oasis/protocol`;
её вызывают и сервер, и клиентское предсказание. Пока формула была продублирована,
стороны разъезжались — это чинилось в плейтесте 22.10.

Коллизий в v0 нет. Единственное ограничение — `clampToZone`: игрок не может
выйти за прямоугольник зоны. Это осознанно: физика — самая дорогая часть
движка, а проверить «мир бесконечен» можно и без неё.

**Почему фиксированный шаг.** Переменный dt от кадра к кадру даёт разную
траекторию на разных машинах. При 20 Гц и предсказании на клиенте это
означает, что два человека, зажавшие W на 5 секунд, окажутся в разных точках.
Фиксированный шаг делает симуляцию детерминированной (при одинаковом вводе).

## 7. Зоны и порталы

Зона — прямоугольник в плоскости XZ с набором пропсов. Мир — набор зон и
порталов между ними.

- `zone_request` возвращает полный `ZoneDef` (включая `props`).
- Клиент кэширует зоны по id; повторный запрос не нужен.
- Портал — круг `(x, z, radius)`. Проверка **на сервере** в каждом тике:
  если игрок внутри круга — телепорт в парную зону.
- Парная зона ищется как портал с обратными `fromZone`/`toZone`. Если его нет —
  игрок остаётся на той же точке (защита от портала-ловушки).
- Клиент по `teleport` запрашивает новую зону и строит её.

Порталы **не** проверяются на клиенте. Клиент рисует кольцо, но решение
принимает сервер — иначе телепорт был бы читерским.

## 8. Чат

- Максимум 240 символов, обрезка на сервере, не на клиенте.
- Rate limit: не чаще одного сообщения в 400 мс и не более 5 в секунду.
- Рассылается всем в секторе (не по AOI): это «общий канал площади».
- Эхо отправителю приходит тоже — клиент не рисует своё сообщение локально.
  Так порядок сообщений у всех одинаковый.

## 8.1. Смена ника (`/name`)

Текстовый ввод, начинающийся с `/`, клиент не отправляет в чат, а разбирает
как команду. Пока команд две: `/name <ник>` и `/help`.

```
клиент                                   сервер
  │ room.send('rename', { name })          │
  │ ──────────────────────────────────────► │ sanitize + uniqueName
  │ ◄────────────────────────────────────── │ renamed { name }
  │ ◄────────────────────────────────────── │ roster (всем)
```

Почему решение принимает сервер, а не клиент:

- **Реестр — серверный.** Ник уникален в пределах сектора без учёта
  регистра. Клиент не видит всех игроков (AOI), поэтому проверить занятость
  не может физически.
- **Ответ — выданный ник, а не запрошенный.** Если имя занято, сервер
  добавляет суффикс (`имя (2)`), и клиент показывает именно `name` из
  `renamed`. Молча подменять нельзя: игрок не поймёт, почему его зовут иначе.
- **Своё же имя не переименовывается.** `uniqueName` исключает саму сессию
  из множества занятых, иначе просьба «оставить как есть» дала бы `имя (2)`.

Клиент запоминает выданный ник в `localStorage` только при явной смене.
Суффикс, полученный при входе из-за совпадения, **не** сохраняется: это
временное разведение двух окон, а не новое имя игрока.

`rename` без `name` или с пустой строкой отбрасывается zod-схемой. Слишком
длинное имя обрезается до 24 символов на сервере, а не рвёт соединение.

## 9. Экономика в протоколе

Ledger — append-only. Каждая запись:

```ts
{ id, accountId, amount, kind, reason, ts, ref? }
```

`balance` приходит в `welcome` и в отдельном сообщении при изменении.

Genesis-грант: `100 ¤` при первом входе. Аккаунт моложе 24 часов получает 20%
(`20 ¤`) — грубая защита от мультиаккаунтов.

Валюта глобальная для аккаунта, а не для мира: `balanceOf(accountId)`
суммирует все миры. Поэтому и genesis — один на аккаунт. Начисление
идемпотентно на двух уровнях: `hasEntry(accountId, 'genesis')` плюс мьютекс
внутри комнаты (две вкладки одного аккаунта) и уникальный частичный индекс
`ledger_entries (account_id) where kind = 'genesis'` в Postgres (два
процесса). `totalSupply(worldId)` при этом остаётся разрезом по миру —
это аналитика, а не граница экономики.

**Известная дыра (D-009).** `accountId` и `accountCreatedAt` присылает клиент.
До появления авторизации любой может представиться кем угодно и «состарить»
аккаунт. Это осознанный компромисс: без auth всё равно нет смысла в
серверной проверке возраста. Закрывается вместе с auth (фаза 2).

## 10. Версионирование

- `PROTOCOL_VERSION` — `major.minor.patch`.
- Несовпадение **любой** части → отказ. Пока нет ни одного внешнего клиента,
  это дешевле, чем поддерживать N версий.
- Layout бинарных пакетов меняется → minor+.
- Появление нового JSON-сообщения → само по себе не ломает старые клиенты,
  но клиент, который его не знает, получит warning от SDK. Поэтому — тоже minor.
- Когда появится второй клиент (нативный/сторонний), вводим `major`-совместимость
  и negotiation. Не раньше.

Константы протокола (`TICK_RATE`, `AOI_RADIUS`, скорости) — часть контракта.
Клиент читает `tickRate`, `aoiRadius` из `welcome`, но скорости зашиты в обе
стороны и меняются только вместе с версией.

## 11. Что проверено тестами

`packages/protocol/test/codec.test.ts`:

1. snapshot round-trip;
2. delta round-trip с удалёнными id;
3. различение типов пакетов;
4. точность позиции в пределах кванта (1/64 м);
5. нормализация курса в 0..2π;
6. размер сущности — ровно 19 байт.

`packages/server/test/vertical.test.ts` (реальный сервер + реальный клиент):

1. welcome, ростер и стартовый снимок приходят, своя сущность в снимке;
2. одинаковые ники разводятся суффиксом, ростер без дублей;
3. переименование через `rename`: успех, конфликт с суффиксом, своё же имя;
4. второй игрок виден и двигается в дельтах;
5. чат доходит до всех, включая эхо отправителю;
6. портал не отправляет игрока обратно (регрессия пинг-понга);
7. портал не срабатывает повторно, пока держишь клавишу (кулдаун);
8. игрок из другой зоны не виден, даже если он в радиусе AOI;
9. ввод протухает: клиент замолчал — сервер не тащит его вперёд;
10. клиент с чужой версией протокола не пускается.

`packages/protocol/test/movement.test.ts`:

1. разгоняется до целевой скорости и не превышает её;
2. разгон не мгновенный: скорость растёт постепенно;
3. останавливается быстрее, чем разгоняется;
4. диагональ не быстрее прямой;
5. ввод длиннее единицы нормализуется, а не даёт форсаж;
6. мёртвая зона: дрожание ввода не двигает персонажа.

Тесты не мокают сеть: Colyseus поднимается в процессе на порту 2620,
клиент — `@colyseus/sdk`. Это медленнее юнит-тестов (~1.7 с), но проверяет
именно то, что ломается в реальности: handshake, порядок сообщений, формат байтов.

## 12. Открытые вопросы протокола

| # | Вопрос | Почему не сейчас |
|---|---|---|
