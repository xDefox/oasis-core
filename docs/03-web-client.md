# Веб-клиент: почему первым и насколько это «приятно»

> Решение: **web-first**. Сервер и формат данных — источник истины; веб-клиент —
> референсная реализация; нативный/VR-клиент — второй клиент к тому же протоколу.

---

## 1. Что изменилось в 2025–2026 (это и перевернуло тему)

- **[реальность] WebGPU** — теперь во всех мажорных браузерах:
  Chrome с **113** (2023), **Firefox 141+** (2025), **Safari 26** (2025).
  Раньше главным возражением против браузера был «всё тормозит на WebGL» — оно перестало
  быть главным.
- **[реальность] WebXR** — Quest Browser даёт полноценный immersive-VR прямо из браузера;
  Safari на Vision Pro поддерживает WebXR (WWDC24); Android Chrome — immersive-AR.
  Adoption WebXR вырос на **~40% за 2026 год**.
- **[реальность] WebAssembly + Web Workers + WebTransport** — появился нормальный
  низкоуровневый стек: компиляция в WASM, вычисления вне главного потока,
  низколатентный транспорт.

**[оценка]** Итого: в 2026 «3D в браузере» перестал быть компромиссом. Он стал
нормальным способом делать продукт.

---

## 2. Где браузер хорош, а где будет больно

| Сценарий | В браузере | Комментарий |
|---|---|---|
| Социалка, чат, торговля, коллекции, казуальные механики | ✅ отлично | Ровно то, ради чего делается «Оазис» |
| Стилизованные / процедурные миры (low-poly, flat shading) | ✅ отлично | 60 fps на среднем ноутбуке, единицы мс CPU на кадр |
| Огромные миры со streaming ассетов с CDN | ✅ отлично | В памяти только окрестности — идеально для «безграничности» |
| UGC-редактор прямо в браузере | ✅ отлично | Главный аргумент за web: тулзы раздаются по ссылке |
| VR на Quest | ⚠️ возможно | WebXR в Quest Browser, но без слоёв SteamVR и с худшей точностью трекинга |
| Реалистичный PBR, тяжёлые шейдеры, массовые draw calls | ❌ больно | Упирается в GPU, а не в сеть |
| Мобильный браузер | ⚠️ троттлинг | 30–60 fps, но через 15–20 минут проседает |
| Крупные C++/Unreal-пайплайны | ❌ больно | Тулзы, дебаг, профилирование, плагины — всё болит |
| Память | ⚠️ лимит вкладки | Нет файловой системы: ассеты через upload/stream/кэш |
| Anti-cheat, DRM, нативные SDK | ❌ нет | Для нашего масштаба неважно |

## 3. Почему web — правильный первый шаг

1. **Ссылка = адрес.** Скачивание клиента убивает воронку. Для найма тестеров
   через Telegram/Discord разница между «ссылка» и «скачай 200 МБ, распакуй, запусти» —
   это порядок аудитории. **Для двух студентов без маркетингового бюджета это
   единственный масштабируемый канал привлечения.**
2. **Нет стора.** Никаких 30%, никакого ревью, никаких вечно висящих обновлений.
   Деплой по 5 раз в день вместо раза в неделю — для итераций это критично.
3. **Instant-on и PWA:** мир открывается в один тап, кэшируется локально, работает
   как приложение.
4. **Один клиент → десктоп + Quest.** WebXR позволяет покрыть и ПК, и шлем без
   второго проекта.
5. **Референсная реализация протокола.** Сервер-авторитет + версионируемый протокол +
   тонкий клиент. Нативный/VR-клиент потом пишется как второй клиент к тому же
   протоколу — дёшево, **если протокол был чистым с первого дня**.

**[оценка]** Обратная сторона: если начать с нативного клиента (Unity/Unreal), через
3 месяца получится «красивый клон Roblox, на две недели позже, чем нужно», причём
протокол окажется привязан к движку, и второй клиент будет невозможен без переписывания.

## 4. Честно: насколько это играбельно и приятно

**[оценка] Главное: «приятность» в социальном мире определяется не картинкой,
а латентностью, отзывчивостью управления и плотностью людей.** Браузер проигрывает
нативному клиенту по «шёлковости» (fps, input lag, тяжёлый рендер), но выигрывает
по всем остальным осям — и для социально-экономической платформы этот обмен выгодный.

### 4.1 Что делать, чтобы было приятно

| Проблема в браузере | Решение | Оценка |
|---|---|---|
| Input lag, «ватное» управление | WebSocket без лишних хопов + edge (Cloudflare) рядом с игроками; клиент шлёт input не чаще **30 Гц** (`INPUT_RATE = 30`, а не на каждый кадр), сервер — тик 20 Гц и снапшоты 10 Гц | Латентность 60–120 мс на близком edge |
| «Телепорт» объектов | **Snapshot interpolation**: клиент экстраполирует между снапшотами, а не ждёт следующий | Плавность 95% случаев |
| Резолв коррекции | **Server-side reconciliation**: клиент переигрывает неподтверждённые инпуты | Задержка визуально не видна |
| Тяжёлый первый заход | Прогрессивная загрузка: сначала 1 сектор low-LOD, потом стримим остальное | Твой вход через 3–8 с |
| Мобильный троттлинг | Снижать LOD по frame-time, не по типу устройства | Стабильные 30–45 fps |
| «Тяжёлый» первый рендер | Canvas 2D-оверлей для UI (DOM) вместо 3D-интерфейса | Нет draw call на каждый элемент UI |

### 4.2 Ориентиры производительности (оценки, цели v1)

| Метрика | Цель |
|---|---|
| fps на десктопе (средний ноутбук, WebGPU) | 60 |
| fps на мобильном (WebGL fallback) | 30–45 |
| Время до первого кадра | < 8 с на 3G/среднем 4G |
| Латентность ввода (edge) | 60–120 мс |
| Размер стартового бандла | < 5 МБ gzip + стриминг |
| Ассет в памяти | только L0–L3 области интереса |

## 5. Клиент: минимальная архитектура

```
┌───────────────────────────────────────────────┐
│ Main thread:  Three.js/Babylon render loop    │
│                (WebGPU device)                │
├───────────────────────────────────────────────┤
│ NetWorker:    WebSocket, протокол,           │
│               снапшоты/дельты, prediction      │
├───────────────────────────────────────────────┤
│ AssetWorker:  загрузка/декодирование текстур, │
│               кэш в Cache Storage / OPFS      │
├───────────────────────────────────────────────┤
│ UI: DOM-оверлей (React/Solid) — чат, инвентарь│
│     тулзы UGC, HUD                            │
└───────────────────────────────────────────────┘
```

**[оценка]** Правило: **рендер не должен блокировать сеть, а сеть не должна блокировать
рендер.** Отсюда NetworkWorker + AssetWorker.

### 5.1 WebGPU vs WebGL

- Основной путь — **WebGPU** (современные API, compute-шейдеры для процедурной генерации
  ассетов на клиенте).
- Fallback — **WebGL 2** (Three.js умеет переключаться автоматически).
- **[реальность]** В 2026 поддержка WebGPU широкая, но у пользователей остаются
  старые машины и мобильные устройства — fallback обязателен, а не опционален.

### 5.2 UGC-редактор в браузере

**[оценка]** Редактор (миры-как-данные) — это отдельный веб-клиент поверх того же API.
В нём:
- инспектор зон/объектов;
- placement глифами по сетке;
- live-превью в том же секторе;
- публикация → новая версия world.json → реестр миров.

**[реальность] Подтверждение, что генеративное 3D-контент production-ready:**
**Roblox Cube 3D** (март 2025) — open source, 1.8 млрд параметров, генерация 3D по
тексту и картинке; **Decart Oasis** (дек. 2024, open source, realtime-генерация) и
**DeepMind Genie 3**. То есть «мир генерируется, а не моделируется руками» — уже не
фантастика, а технология, которую можно использовать для наполнения.

## 6. VR (WebXR): план, в фазе 1 не делаем

**[оценка]** Режим WebXR в том же клиенте:
- `navigator.xr.requestSession('immersive-vr')` → рендер в стерео;
- WebXR-слои (StereoLayer) поддерживаются;
- ограничения: нет SteamVR-оверлеев, точность трекинга ниже, нет нативного hand-tracking
  уровня Meta, нагрузка на GPU Quest высокая → **нужен более низкий бюджет LOD**.

**План:** сначала «картинка + базовое перемещение» — чтобы проверить спрос,
полноценный VR — отдельный этап, если будет аудитория. В коде WebXR сегодня
не используется вовсе: в фазе 1 не делаем (§4.3 плана), возвращаемся в 3–4.

## 7. Что делать, если «не заходит»

**[оценка]** Триггеры, при которых переходим с web на нативный клиент:

| Триггер | Решение |
|---|---|
| Нужна VR 120 fps на Quest | Нативный клиент на Unity (SteamVR/OpenXR) по тому же протоколу |
| Нужен реалистичный рендер | Unity/Unreal — тот же протокол, те же данные мира |
| Веб-клиент не тянет 100+ онлайн в секторе | Увеличить размер сектора (меньше шардов) — **это не про клиент** |
| Пользователи просят приложение в сторе | PWA + обёртка (Tauri) — без комиссии и ревью |

**[оценка]** Главное правило: **переход на нативный клиент не должен требовать переписывания
сервера и мира.** Для этого протокол версионируется и не зависит от движка.
