## 1. Правила игры

**Владелец модуля — один.** Файл, за который отвечает один человек, другой
не правит напрямую, даже если «надо быстро». Быстро — это ветка + PR + ревью
на 5 минут. Медленно — это два человека, одновременно переписывающих `codec.ts`
в разных направлениях.

| Правило | Как выглядит |
|---|---|
| Ветки | `main` защищён. Всё через PR. Мерджит автор после approve. |
| Размер PR | ≤ 400 строк диффа. Больше — режем на части, иначе ревью превращается в «ок». |
| Протокол | Любое изменение `packages/protocol` — только PR с ревью второго. Оба подписываются. |
| Версия | Меняется `PROTOCOL_VERSION` в том же PR, где меняется layout. Отдельным PR — никогда. |
| Тесты | Новый код в `protocol` и `server` — с тестом. Клиент — по здравому смыслу, но ручной чек-лист обязателен. |
| **Тест должен ловить свой баг** | **Новый тест обязан падать, если убрать его фикс. Проверяется мутацией, а не «на глаз».** |
| Definition of Done | (1) `npm run typecheck` зелёный, (2) `npm test` зелёный, (3) работает вживую, (4) описание в PR: что проверил руками. |
| Созвоны | 1 раз в неделю, 30 минут: демо + блокеры. Всё остальное — текстом в PR. |

### 1.1. Правило «тест должен ловить свой баг»

Это отдельное правило, потому что мы дважды наступили на грабли.

**Что случилось.** 22.10 мы добавили тест «игрок из другой зоны не виден». Он был
зелёным. Потом я откатил фикс — а тест остался зелёным. Оказалось, тест ловил
не «другая зона», а «игрок ушёл дальше 24 м»: игрок успевал уехать за радиус
раньше, чем проверка срабатывала. Ещё раз: зонд движения не ловил сломанный
разгон, потому что мерял скорость через 1.5 с — к этому моменту и с ускорением,
и без него скорость уже 5 м/с.

**Почему это опасно.** Тест, который проходит и на сломанном коде, хуже, чем
его отсутствие: он создаёт ложную уверенность. Человек видит зелёную галочку и
перестаёт смотреть на код.

**Как проверять.** Мутация: убрать фикс, убедиться, что нужный тест упал.

```bash
node scripts/mutation-check.mjs   # ломает код по одному и ждёт падения
```

Скрипт в CI. Если новая мутация выжила — значит соответствующий тест слабый,
и это надо чинить, а не «потом».

**Что делать, если мутацию нельзя поймать тестом.** Иногда защита дублирует
другую (например, кулдаун портала дублирует «прибытие за порогом»). Тогда
мутация помечается в списке как «покрыта другой защитой» — с комментарием,
почему это не дыра. Молча пропустить нельзя.

**Правило для браузерных зондов.** Зонд (`scripts/probes/`) — тоже тест, и он
тоже должен падать на сломанном коде. Проверено 22.10: откат фикса «призрак»
валит `zone-exit.mjs`, откат разводки ников валит `names.mjs`, откат разгона
валит `world.mjs`, откат разбора `/name` валит `rename.mjs` восемью пунктами.

**Зонд не должен зависеть от fps.** Headless-браузер в CI рисовал 3 fps, а
проверка разгона считала кадры и падала на зелёном коде. Правильная единица —
тик симуляции (50 мс): он фиксированный, кадр — нет. Поэтому клиент отдаёт
`simTicks` в `__oasisDebug`, а зонд проверяет прирост скорости за тик, а не
«есть ли промежуточная скорость в выборке». Заодно обязательно нужен образец
**в покое** до нажатия клавиши: без него скачок 0 → 5 не с чем сравнить, и
сломанный разгон проходит незамеченным (проверено — мутация не падала).

Оценки ниже — **часы чистой работы** (не «время у компьютера»). Реальность:
умножайте на **1.6–2.0** — на отладку окружения, ревью, «почему на проде
другое», и на то, что вы студенты с сессией.

### 1.2. Как «main защищён» enforced в GitHub

Правило «`main` защищён» из таблицы выше — не договорённость, а настройка
репозитория. С 22.10 репозиторий публичный, и на `main` включён ruleset
(`Settings → Rules → Rulesets → main-protection`):

| Правило GitHub | Что запрещает |
|---|---|
| Required pull request | пуш в `main` мимо PR — включая пуш владельца репозитория |
| 1 approving review | мерджит без ревью второго человека |
| Require last push approval | approve перестаёт считаться, если автор пушил в ветку ещё раз |
| Required status checks | `typecheck + tests`, `проверка мира`, `мутации (тесты не врут?)`, `headless-мир` |
| Strict status checks | ветка должна быть обновлена относительно `main` перед мерджем |
| Non-fast-forward + linear history | force-push и merge-коммиты в `main` |
| Required conversation resolution | PR не мерджится с нерешёнными комментариями |

Обходных путей нет: список bypass-акторов пуст, админ тоже подчиняется правилам.

Владельцы модулей — в [`.github/CODEOWNERS`](../.github/CODEOWNERS).
`packages/protocol/**` закреплён за вторым человеком, поэтому PR с правкой
протокола без его approve не мерджится — это техническая реализация правила
«Протокол», а не просьба.

**Если работаем в одиночку** и второй человек недоступен: снять ruleset —
`Settings → Rules → Rulesets → main-protection → Delete`. Вернуть — создать
заново через API (команда лежит в описании PR, который вводил правило).

## 2. Карта владения

### A — сервер, протокол, инфраструктура

```
packages/protocol/src/constants.ts      контракт, скорости, лимиты
packages/protocol/src/codec.ts          бинарные пакеты
packages/protocol/src/types.ts          модели и payload'ы
packages/protocol/src/validation.ts     zod-схемы
packages/protocol/test/                 тесты кодека и движения
packages/protocol/schema/*.json         JSON-схемы мира и ledger
packages/server/**                      всё
content/default/world.json              генерируется скриптом, коммитится
scripts/dev.mjs                         dev-раннер
scripts/browser-test.mjs                раннер браузерных зондов
scripts/mutation-check.mjs              мутационная проверка тестов
docker-compose.yml, .env.example        инфраструктура
.github/workflows/**                    CI
```

### B — клиент, рендер, UX

```
packages/client/index.html              разметка HUD
packages/client/src/style.css           оформление
packages/client/src/main.ts             сборка кадра
packages/client/src/net/**              транспорт, интерполяция, предсказание
packages/client/src/render/**           сцена, аватары, порталы
packages/client/src/input/**            управление
packages/client/src/ui/**               HUD, чат
packages/client/vite.config.ts          сборка
scripts/probes/**                       браузерные зонды
docs/03-web-client.md                   клиентская часть документации
```

### Общее (менять только вместе)

```
packages/protocol/src/index.ts          публичный API протокола
packages/protocol/src/movement.ts       модель движения: общая для клиента и сервера
content/default/world.json              A генерирует, B проверяет, что клиент его переваривает
scripts/probes/_probe.mjs               общий помощник зондов: A правит, B согласует
docs/10-protocol-v0.md                  A пишет, B читает и спорит
docs/11-work-plan.md                    этот файл: правим оба
```

**Граница, которая держит проект целым:** B может читать `protocol` и предлагать
изменения, но не редактирует его в своей ветке. Если B нужен новый тип пропса —
он пишет A задачу в issue, A добавляет в схему + валидацию + тест, и только
потом B это использует. Иначе клиент начнёт «поддерживать» тип, которого сервер
не знает, и мы получим два протокола.

### 3.1. Ревью 21.10: что нашли и починили

Читали код как чужой — с прицелом «что сломается в руках двух живых людей».

## 6. Чек-лист ревью протокола

Если PR трогает `packages/protocol` — второй человек проверяет именно это:

- [ ] `PROTOCOL_VERSION` изменён, если изменился layout бинарных пакетов.
- [ ] Новые константы добавлены в `constants.ts`, а не зашиты числом в кодек или симуляцию.
- [ ] Клиент и сервер читают одно и то же число из протокола (нет второй копии скорости/AOI).
- [ ] Round-trip тест на новое поле в `codec.test.ts`.
- [ ] Квантование не теряет точность сверх заявленной (1/64 м).
- [ ] Новое JSON-сообщение описано в `docs/10-protocol-v0.md` (C→S и S→C таблицы).
- [ ] Валидация в `validation.ts`, а не «доверимся, что клиент пришлёт число».
- [ ] Изменение не ломает интеграционный тест на двух клиентов.
